# Multi-Orb Collaboration

## Intent

Measure multi-Orb collaboration by how much correct work survives after changes occur, not by how many Orbs start at once. The Git remote is the sole shared authority for source code and lineage. Thread messages carry only tasks, status, blockers, and authority deltas, not source snapshots.

This protocol is responsible only for safely mapping workstreams already proven to be parallelizable onto independent Orbs:

- `buildable-plan` decides workstreams, ownership, contracts, and joins.
- `impl-loop` decides the current ready frontier and the closure affected by changes.
- This document governs the lifecycle of baselines, branches, delivery, and integration across Orbs.

## Choose execution boundaries

An independent Orb is suitable only for a long-running task whose inputs are committed and available from the remote, whose write ownership is independent, whose consumed contract authority has joined or been released at that baseline, which does not depend on implementation artifacts from another worker in the same wave that have not yet been integrated, which can be verified independently, and whose join is explicit.

Keep the following work in the current Orb, using a subagent in the current environment or serial execution:

- It depends on the main agent's uncommitted state.
- The contract is still being explored collaboratively.
- The work requires frequent sharing of intermediate results.
- The cost of cloning, setup, and integration exceeds the benefit of parallelism.

Do not use tar archives, patches, file uploads, or `amp sync` as a substitute for shared Git authority across multiple Orbs. They may carry logs, diagnostics, or copies for human inspection, but they do not establish shared lineage.

## Authority and branches

Each wave of multi-Orb collaboration has exactly one integration owner and one remote authority ref. Keep the authority history traceable. Multiple agents must not write to it concurrently or force-push it.

```text
origin/integration/<task>    # exclusive to the integration owner
origin/work/<task>/<id>      # exclusive to each worker Orb
```

When repository policy allows it, the authority may use an existing integration branch. User authorization is required before creating or writing a remote branch. Without authorization, keep the work in the current Orb; do not bypass this rule with a file overlay.

Before starting a wave, the integration owner commits and pushes the source code, canonical requirements, shared contract authority, schemas, fixtures, and verification entry points required by the workers, and records the exact `base_sha`. The join or release evidence for every consumed authority must correspond to this baseline. When the PLAN sets a representative vertical-slice gate for a new contract, that gate must pass before its direct dependents start. A semantic freeze alone does not constitute worker release evidence.

## Orb Transport Envelope

Each Orb uses the bounded task contract from `impl-loop`. This document does not duplicate its goal, ownership, contract, invariant, verification, or survival fields. An independent Orb adds only this Git transport envelope:

```text
workstream_id
authority_ref
base_sha
worker_branch
integration_owner
```

The prompt also carries the task contract generated by `impl-loop` and references the canonical contract at `base_sha`. Do not write a separate semantic definition. When the goal, ownership, shared contract, or dependency topology changes, return to `buildable-plan` for revision and obtain `ready` again. This document does not issue or rewrite workstream contracts.

## Worker Lifecycle

A new Orb starts from a fresh clone. Do not assume its initial checkout is the specified baseline. The worker must fetch the remote, confirm that `base_sha` is reachable, and create its own branch from that SHA. Report `BLOCKED` when the baseline or a load-bearing input is unreachable.

The worker:

- Modifies only `owns`. Shared contracts and other workstream surfaces are read-only.
- Does not consume another worker's branch before it has been integrated.
- Stops and reports `DESIGN-DELTA` when the contract is underspecified, contradictory, or must change. The worker does not modify shared authority or add a workaround on its own.
- Commits and pushes deliverable source code and tests to its own remote branch.
- After committing all deliverable changes, runs local validation against the exact `head_sha` in a clean working tree, then pushes and delivers that same SHA. It does not deliver an uncommitted working tree or a movable branch name.

The worker may report only local completion:

```text
READY-CANDIDATE
workstream: <id>
branch: <remote-worker-branch>
base: <base-sha>
head: <head-sha>
validated-head: <head-sha>
owned-diff: <paths-or-symbols>
consumed-contracts: <contracts-and-assumptions>
local-validation: <checks-and-results>
open-design-delta: none
join-validation: <required-checks>
```

## Integration Acceptance

Only the integration owner can determine integration completion under the current authority. After receiving `READY-CANDIDATE`, perform a small join promptly rather than accumulating multiple branches awaiting integration:

1. Fetch the authority and worker refs, then verify that the base and head are reachable and have valid lineage.
2. Check whether the worker diff crosses its ownership boundary.
3. Check whether changes from the worker base to the current authority affect its goal, consumed contracts, prerequisites, validation premises, or `survives_if`.
4. Construct a candidate joined tree from the current authority and worker head.
5. Run join validation and applicable reviews on the joined tree.
6. Confirm that the authority did not change during validation, then integrate according to repository policy and advance the authority ref.

When admission fails, the integration owner does not modify the worker branch. Report `BLOCKED` when the base or head is unreachable or an environment prerequisite is missing. For a worker-local defect, mismatched validation evidence, or an ownership violation, leave the authority unchanged and return the evidence to the worker owner. When a semantic change in the current authority invalidates the candidate, have `impl-loop` classify the work and the affected closure. If the change involves the goal, ownership, shared contract, or dependency topology, pause the affected workstream, return to `buildable-plan`, and do not dispatch it again until it obtains `ready`.

A worker branch being behind, having a different commit count, or not yet being rebased does not by itself mean it is stale. Integrating an unrelated workstream should not force correct work to be redone. Existing join or release evidence may carry forward to a descendant authority, but the integration owner must record an authority-delta impact check confirming that the consumed contract, prerequisites, validation premises, and `survives_if` remain unchanged.

The durable state after integration is:

```text
INTEGRATED
workstream: <id>
worker-head: <head-sha>
authority: <new-authority-sha>
join-validation: PASS
```

## Authority deltas and stale work

Only the integration owner may modify shared authority. After a load-bearing authority changes, publish:

```text
AUTHORITY-DELTA
old: <old-sha>
new: <new-sha>
changed-contracts: <semantic-changes>
evidence: <diff-or-locators>
```

`AUTHORITY-DELTA` carries only the Git authority change and its evidence. Based on the canonical workstream contract, `impl-loop` computes the affected closure, classifies the work, and determines what continues, pauses, or requires revalidation. This document does not maintain a second set of stale criteria. If closure analysis finds a change to ownership, the shared contract, or dependency topology, return specifically to `buildable-plan`. Resume an affected write task only after the new PLAN becomes `ready` again.

Advancing the authority alone, integrating other independent workstreams, or a branch merely falling behind does not make work stale. An unreachable base or head is a transport blocker and must not be presented as semantic staleness.

Thread messages may be delayed, so stop or delta notifications only accelerate the response. When accepting a candidate result, the integration owner must still fetch again and independently inspect the current authority. Do not rely on the worker having received a message promptly.

## Review Milestones

- Leaf: Check ownership, local validation, applicable `lifeguard.y[a]ml` rules, and read-only surfaces.
- Join: Check the real producer-consumer path, contract interpretation, and integration tests on the candidate joined tree.
- Milestone: At the first representative end-to-end join, after a load-bearing design delta, and before final delivery, compare user intent with the actual implementation against the canonical user requirements.

Do not repeat a full requirements review after every mechanical small join.

## Recovery

- Orb failure or suspension: If the head has been pushed, another Orb can continue from that SHA. The machine and thread do not own the work product.
- Missing execution-environment prerequisite: Mark it `BLOCKED` for the environment owner to fix. Do not add a source overlay to an individual Orb. Return owner-local source or dependency omissions to the corresponding workstream, then integrate them through the worker branch and normal admission. Give migration, schema, shared dependency, or topology changes to `impl-loop` as `DESIGN-DELTA` for classification. When necessary, return to `buildable-plan` to obtain `ready` again. Recompute the affected closure after integrating the fix.
- Producer output becomes consumer input: Integrate the producer and advance the authority before dispatching the consumer. A worker branch does not become a shadow authority.
- Authority advances during join validation: Discard the admission conclusion and reevaluate against the new authority. Do not assume the work is fresh or stale.
